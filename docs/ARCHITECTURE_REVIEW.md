# ARCHITECTURE_REVIEW.md — Архитектурная критика

> **Что это.** Профессиональный разбор реализаций: Unity-легаси, текущего вынесенного ядра и
> разделения проектов. В отличие от `KNOWN_ISSUES.md` (реестр долга, кратко) здесь — глубинная
> критика с файл:строка, влиянием и рекомендацией. Связано: `BATTLE_PARITY.md` (механики-разрывы),
> `TARGET_LAYOUT.md` (целевая декомпозиция), `UNITY_LEGACY_MAP.md` (карта классов).
>
> **Принцип разбора:** слои и границы → инварианты (из `ARCHITECTURE.md` §3–4 и `AGENTS.md`) →
> связность/дублирование → мёртвый код → консистентность (код vs доки). Критика конструктивная:
> каждый пункт заканчивается рекомендацией.

## 1. Unity-легаси

### 1.1 God-классы: смешение всех ответственностей

| Класс | Строк | Проблема |
|---|---|---|
| `RaidSceneManager` | 6043 | Оркестрация боя + UI + события + данные + FMOD-вызовы в одном классе. Мультиплеер наследует его и перекрывает — ветвление по режиму в 6к строк |
| `DarkestDatabase` | 2408 | «Каталог всего контента»: герои/монстры/скиллы/квирки/локализация/город — единый монолит, весь кэш в статике |
| `SaveLoadManager` | 1870 | Сериализация + UI сейвов + флоу + deadlock-ы (см. `KNOWN_ISSUES.md` §11) |
| `Character` / `BattleGround` / `Effect` | 1223 / 1060 / 772 | Крупные классы с портативным ядром, зашитым внутрь |

**Влияние:** невозможно покрыть тестами, высокий порог входа, конфликты мержей, риск регрессий.
**Рекомендация:** не «разбивать на месте» (легаси живёт до cutover) — выносить логику в ядро
целыми блоками (что и происходит); остальное остаётся до Фазы 6.

### 1.2 Глобальное состояние вместо DI

`DarkestDungeonManager.Instanse.database` → `DarkestDungeonManager.Data` (`DarkestDungeonManager.cs:40`) —
глобальный статический доступ к контенту из любой точки (`RaidSceneManager.cs:626, 4212, 4332...`).
**Влияние:** тесты требуют инициализации глобального состояния; порядок загрузки неявный; скрытые
зависимости. **Рекомендация:** в ядре уже запрещено (`AGENTS.md` Constructor DI) — при выносе
инжектировать; легаси не трогаем.

### 1.3 Корутины как весь игровой флоу

Весь бой/переходы/анимации на корутинах (задержки, последовательности). **Влияние:** недетерминизм,
сложно реплицировать и тестировать, «гонки» в мультиплеере. **Рекомендация:** ядро — чистая
симуляция + события; корутины остаются только в view (`ARCHITECTURE.md` §4.4).

### 1.4 Магические строки эффектов

`DarkestDungeonManager.Data.Effects["Stress 2"]`, `["AfflictedAllyStress"]`, `["Heal Stress 1"]`,
`["Heal Stress Chance 1"]` (`RaidSceneManager.cs:626, 782, 1818, 4212, 4332–4340, 4591, 5941`).
**Влияние:** опечатка — молчаливый null, рефакторинг контента ломает бой без диагностики.
**Рекомендация:** в ядре — `nameof`/константы на месте определения + валидация на загрузке.

### 1.5 RPC-репликация против локстапа (дуэль)

`RaidSceneMultiplayerManager`/`MultiplayerSync` — общее состояние + RPC + readiness-барьеры.
Сид-хак `player.ID + player.ToString().GetHashCode()` (`RaidSceneMultiplayerManager.cs:31-49`) —
нестабилен между рантаймами (см. `KNOWN_ISSUES.md` §5). **Влияние:** сложно, гонки, дебаг ада.
**Рекомендация:** модель уже заменена `Core.Duel` (локстап, `DuelSeed`); cutover — Фаза 6.

### 1.6 Дублирование оркестрации (два wire-протокола)

Та же PvP-модель описана в Unity (RPC-строки) и в `Core.Duel` (`DuelPayload`). Два источника истины.
**Рекомендация:** сводить к `Core.Duel` (`DUEL_ARCHITECTURE.md` §4.1, Фаза 6).

### 1.7 Мёртвый/дефектный код

- `PoisonStatusEffect.Type` возвращает `StatusType.Bleeding` (баг) — не проявляется, т.к. поиск идёт
  по ключу словаря.
- `.riposte_chance_add` парсится и выбрасывается (`Effect.cs:436-440`) — рипост всегда 100%.
- Закомментированные трайт-тесты в `HeroTurn` (`RaidSceneMultiplayerManager.cs:1355-1356`).
**Рекомендация:** фиксировать как известный долг; не чинить в легаси (минимальный дифф).

## 2. Текущее ядро (`src\Core\`)

> **Статус на конец доменного разделения** (задача «библиотеки под домены»): ядро разбито по доменам
> (`Core.Common`/`Content`/`Combat`/`Campaign`/`Raid`/`Save`/`Duel` + клиентская граница
> `Clients.Content`), `Core.Data` распущен. Закрытые пункты ниже помечены **✓**. Остались открытые —
> как было.

### 2.1 Нарушение слоёв: `Core.Data` → `Core.Duel` — **✓ закрыто**

`TextFightContent` (реализация `IDuelContent`) переехал в `Core.Duel\Fight`; проект `Core.Data` удалён.

### 2.2 Несогласованный принцип «данные = домен» — **✓ закрыто**

DTO+мапперы квирков/баффов/трайтов — в `Core.Content`/`Core.Combat`
(`Database\JsonBuff.cs`, `QuirkMapper.cs`...), а DTO кампинга/тринкетов/квестов/городских событий —
в `Core.Data\Dto\`. Один принцип применён двумя способами. **Влияние:** два места поиска данных,
неоднозначность для агентов. **Рекомендация:** единое правило — DTO+парсер+каталог живут в модуле
своего домена; `Core.Data` не существует как модуль (см. `TARGET_LAYOUT.md`).
> **Исполнено:** DTO/парсеры/каталоги разведены по доменам (`Campaign`/`Raid`/`Content\Camping|Trinket`/
> `Combat\AI`), `GameDataReader` — тонкий Newtonsoft-фасад в `Clients.Content`.

### 2.3 Инвариант «ошибки через Result» не исполнен — **✓ закрыто**

`ARCHITECTURE.md` §4.1 требует `Result`/`Result<T>`; фактически `Result` есть только в
`src\Lan\...Contracts\Results\` и в ядре **не используется** (0 файлов). Ядро молча возвращает `null`
(`EffectCatalog.Get` → null, `IDuelContent.Get*` → null). **Влияние:** инвариант декларативный;
call-site'ы без проверки падают NRE. **Рекомендация:** перенести `Result` в `Core.Common` и применять
на новых API **или** признать null-модель и переписать инвариант в `ARCHITECTURE.md`.
> **Исполнено (частично):** `Result`/`Result<T>` переехали в `Core.Common` (транспорт `Lan.Contracts`
> ссылается на `Common`). Применение на новых API ядра — постепенно; null-модель в существующих
> `Get*` остаётся как известный стиль.

### 2.4 Инвариант «полиморфизм вместо switch» нарушен в вынесенном коде

`switch` в `Character.cs:387, 402, 427, 548, 565` (диспатч `BuffType`/`BuffRule`), в парсерах
(`HeroClassFileParser.cs:68`, `MonsterClassFileParser.cs:67, 226`) и AI
(`BonusInitiativeDesire.cs:47`, `BonusInitiativeAllyClassCount.cs:54`, `BonusInitiativeAllyLastDamaged.cs:48`).
**Влияние:** код портирован с legacy-стилем, конфликтует с собственным правилом. **Рекомендация:**
для портированного кода зафиксировать исключение в `AGENTS.md` (портируем как есть, рефакторим только
при реальной задаче) ИЛИ заменить на словари/стратегии при выносе-рефакторинге.

### 2.5 Мёртвый код и непотреблённые статусы

Классы-эффекты/статусы вынесены, но **ничего не потребляют**:
`DamageOverTimeStatusEffect.CurrentTickDamage` (`:15`), `StunStatusEffect.UpdateNextTurn` (пуст),
`RiposteSkill` (никогда не исполняется), `GuardEffect` (недостижим — нет `.guard` в каталоге),
`KillEffect.MarkedForDeath`, `DeathsDoorStatusEffect`. Полный разбор — `BATTLE_PARITY.md`.
**Влияние:** «вынесено, но не работает» — ложное ощущение готовности. **Рекомендация:** закрыть
паритет-разрывы в ядре (приоритетный список в `BATTLE_PARITY.md` §5).

### 2.6 Дублирование логики применения баффов

`CombatStatBuffEffect.ApplyBuff` (`CombatStatBuffEffect.cs:240-281`) и `BuffEffect.ApplyBuff`
(`BuffEffect.cs:181-202`) — две реализации «создать `BuffInfo` + ролл дебафф-резиста + длительность».
**Влияние:** расхождения правил (порог, клэмп) между путями. **Рекомендация:** единая фабрика
`BuffInfo`/метод на `Character`.

### 2.7 Stale-документация в коде

Шапка `EffectCatalog.cs:10-17` утверждает, что `.combat_stat_buff`/`.buff_ids` — «pending»,
хотя реализованы (`:143-167`). **Влияние:** агенты ищут несуществующую работу. **Рекомендация:**
обновить XML-док в коммите фикса (это «документированный факт»).

### 2.8 Newtonsoft в `Core.Data` против Unity 2017.4 — **✓ закрыто**

`Core.Data` добавляет `Newtonsoft.Json 13.0.3` (netstandard2.0), а `KNOWN_ISSUES.md` §13 фиксирует:
сборки Newtonsoft ссылаются на net6.0-контракты и не читаются компилятором 2017.4 (CS0009).
**Влияние:** «единый ридер для всех клиентов» не доставится в `unity-2017\` как есть.
**Рекомендация:** проверить фактическую доставку; при невозможности — десериализация остаётся на
границе презентации (как в `Core.Content`), в ядре — только DTO + мапперы.
> **Исполнено:** `GameDataReader` + Newtonsoft — на клиентской границе (`Clients.Content`); доменные
> модули чистые. Напряжение 2017.4-vs-Newtonsoft остаётся как `KNOWN_ISSUES.md §13` (для стенда).

### 2.9 `Core.Ui` — аморфный модуль

Два файла (`UiStyle`, `ArgbColor`) — «презентационные токены» в ядре. Не домен, не транспорт.
**Влияние:** размывает понятие «чистое ядро = домен». **Рекомендация:** перенести в общий
клиентский shared-проект (или `Wpf`/Unity-общий) — см. `TARGET_LAYOUT.md`.

### 2.10 AI дуэли: жёсткий дефолтный брейн

`DuelAi.BuildDefaultBrain` (`DuelAi.cs:54`) хардкодит брейн для PvP; `IDuelContent.GetMonsterBrain`
(`IDuelContent.cs:34`) используется только Fight-путём (`DuelController.cs:201`). Кампанийные мозги
не применяются в дуэли. **Рекомендация:** грузить кампанийный брейн в PvP (наши желания уже
зеркалят DD — `AI_BEHAVIOR.md`) или документировать намерение.

### 2.11 Дублирование парсеров DSL

`HeroClassFileParser` и `MonsterClassFileParser` — два независимых парсера с дублирующимся
токен-кодом (split-respecting-quotes, percent, префиксы), плюс третий парсер — `EffectCatalog`.
**Влияние:** расхождения форматов, тройная поддержка. **Рекомендация:** общий низкоуровневый
токен-парсер в `Core.Common`/`Content`, специализации поверх.

## 3. Разделение проектов (дизайн-вопрос «данные = домен»)

### 3.1 Тезис

**Данные — это домен.** DTO, парсеры, каталоги и мапперы несут знание о домене (что такое
`Quest`, `Trinket`, `CampingSkill`, как их парсить) — это не инфраструктура. Кладя их в отдельный
«данные»-модуль, мы создаём модуль без связности: он не про один домен, а про все сразу.

### 3.2 Критика текущего сплита

- `Core.Data` — «свалка всех данных всех доменов» (Camping + Trinkets + Quests + TownEvents +
  Buildings + Provision + Roster + Curios + monster brains). Нарушает «модуль = папка = домен»
  (`AGENTS.md`) и правило связности: изменение квеста трогает «данные», а не «кампанию».
- Смешанный стиль размещения (п. 2.2) — результат исторического роста: сначала DTO-мапперы
  легли в `Content`, потом «единый ридер» создал второй дом.
- Newtonsoft в ядре (п. 2.8) — второй разрыв: **десериализация — это внешняя граница**, её место
  на краю приложения (Unity/WPF), а не в домене. Домену достаточно DTO (snake_case по legacy-JSON)
  + чистых мапперов.

### 3.3 Вывод

Двигаться к «данные = домен»: каждый доменный модуль владеет своими DTO+парсерами+каталогами;
единая точка чтения файлов (`GameDataReader`) остаётся тонким фасадом для клиентов (и может жить
в презентации или в тонком слое чтения). `Core.Data` как модуль — распустить. Конкретика —
`TARGET_LAYOUT.md`.
