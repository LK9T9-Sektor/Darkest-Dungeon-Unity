# NETWORK_RATIONALE.md — Почему не встроенный Unity-неткод

Объяснение выбора сетевого слоя: почему встроенный Unity-неткод не нужен, как Photon используется в проекте на самом деле, и почему целевое направление — байтовый транспорт `ITransport` + собственный session-слой. План миграции — в `NETWORK_LAYER_REUSE.md`, текущий факт — в `NETWORK.md`, session-модель — в `FEATURE_GAME_MODES.md`.

## 1. Два разных «NetworkBehaviour»

Существуют две разных вещи, которые называют «NetworkBehaviour»:

1. **`UnityEngine.Networking.NetworkBehaviour` — встроенный Unity-неткод (UNET).**
   Модель — `NetworkIdentity`/`NetworkBehaviour` на каждом сетевом префабе: компонент на объекте, разметка в сцене, «RPC-магия». UNET deprecated с 2019; наследник — «Netcode for GameObjects» с той же моделью (`NetworkObject` на каждый объект). Боль «добавлять сетевой компонент на каждый префаб» реальна, но только если использовать встроенный Unity-неткод.

2. **Photon PUN — ассет, а не движок.**
   Свой компонент `PhotonView`, свои классы `PunBehaviour` и `[PunRPC]`. Философия похожая («навесил PhotonView, разметил RPC»), но это сторонний пакет, а не часть движка.

Вывод: `NetworkBehaviour` нужен **только** для встроенного Unity-протокола. Photon, Steam и любой другой транспорт его не используют и не требуют.

## 2. Что реально использует проект

Проверено по кодовой базе (актуальные цифры):

| Метрика | Значение |
|---|---|
| Вызовы `PhotonNetwork.*` | 65 (лобби, комнаты, `isMasterClient`, `LoadLevel`…) |
| Методы `[PunRPC]` | 8 — все в `PhotonGameManager.cs` |
| Вызовы `photonView.RPC(...)` | 2 — `PhotonGameManager.cs:27`, `MultiplayerSync.cs:366` |
| Размер `PhotonGameManager.cs` | ~120 строк (hub-паттерн) |
| Папка `Assets\Scripts\Networking` | ~4.3k строк |

Ключевой нюанс: RPC **не размазаны по префабам**. Все вызовы идут через единственный `PhotonView` на hub-объекте `PhotonGameManager`. Поэтому боль «добавлять сетевой компонент на каждый префаб» в текущем коде уже не существует — PUN используется аккуратно.

Steam-режим (версия 1.0.5/1.0.6) уже идёт через чистый транспорт `ITransport` из `src\Lan\Sektor.DarkestDungeon.Lan.Contracts\Transport\`: сессия = события (`SessionJoined`/`PlayerJoined`/`MessageReceived`…), сообщения — `SendMessage(type, payload)`, ошибки — `Result` вместо исключений. Транспорт только доставляет байты и не владеет состоянием игры.

## 3. Ответы на исходные вопросы

- **NetworkBehaviour нужен только чтобы использовать встроенный Unity-протокол?** — Да. `UnityEngine.Networking.NetworkBehaviour` — только для встроенного Unity-неткода. Photon, Steam и остальное его не используют.
- **Photon делает так же?** — Нет. Photon — не Unity-неткод, у него свой механизм (`PhotonView`/`[PunRPC]`). Но философски похоже (сетевые компоненты на объектах).
- **Не придётся мучаться и задавать на сцене специальные сетевые компоненты, добавлять туда каждый префаб?** — Нет. С интерфейсом `ITransport` + Steam сетевая логика вообще не знает о компонентах: `SendData(bytes)` / `ReceiveData(bytes)`. Ноль Unity-компонентов, ноль настройки сцен, ноль префабов, ноль RPC, ноль магических строк. Игровая логика сама решает, какие байты слать; MonoBehaviour-ы остаются как есть (только рендер/ввод). Аналогия — «Warcraft-мост»: игра о Steam не знала, мост просто гонял пакеты.

## 4. Честная цена свободы

- Photon/UNET дают «RPC-магию» (вызвал метод на чужих клиентах) ценой компонентов + магических строк + привязки к движку.
- Байтовый транспорт даёт только байты → свой слой сообщений (сериализация команд, маршрутизация, authority, детерминизм) строишь сам. Это и есть session-модель из `FEATURE_GAME_MODES.md`.

При цели (кооп 1–8 + независимость от движка) выбор однозначен: байтовый транспорт + собственный session-слой, ноль сетевых компонентов.

## 5. Куда уходят текущие Photon-вызовы

Текущие 65 вызовов `PhotonNetwork.*` и RPC — это ровно тот код, который ложится за интерфейс `ITransport` (либо за статический фасад `MultiplayerSync`, который уже переключает Steam/Photon в рантайме — см. `CHANGELOG.md` 1.0.5/1.0.6). Игровая логика общается с транспортом, а не с провайдером; конкретная реализация подставляется фабрикой.
